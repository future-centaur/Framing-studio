## 1. What the system is and why it exists

A framing-order website with two entry paths — direct client purchase and photographer-mediated purchase — built around a live configurator that composites a client's own uploaded photo into a chosen moulding/mat/glazing/mount combination, in real time, with a live KES price total. Photographers can either refer clients (earning commission) or purchase wholesale on a client's behalf for resale (earning a studio discount), never both in one transaction. The system exists to replace an undifferentiated, ambiguous photographer relationship with one that has explicit, separately tracked economics, on a studio-brand-agnostic platform ("Hollow & Hale" is placeholder identity, not fixed product identity).

## 2. Core entities and their relationships

- **Catalog Item** (moulding / matting / glazing / mounting) — data-driven record: name, image, price (KES), tier (budget/mid/premium), **archival description** (concrete material/UV-blocking specifics — e.g. "99% UV-blocking, museum-grade acrylic," never generic phrasing like "gallery quality"). *(enforced in §4 catalog endpoint, §6 catalog data layer, D-7)*
- **Configuration** — one client's or photographer's selected combination of catalog items + uploaded photo reference. Produces a live preview and a live price.
- **Order** — one Configuration, priced and committed. Belongs to exactly one Cart.
- **Cart** — one or more Orders checked out together. Has exactly one `path`: `referral`, `resale`, or `direct` (a named, practitioner-confirmed path — client purchase with no photographer involved, skips commission/discount/approval entirely). *(enforces D-15 — one path per cart; A-13 — direct path)*
- **Photographer** — account entity, created via phone/email + self-declared "is this you?" checkbox, no verification. *(enforces resolved C-3)*
- **Referral Link** — generated by a Photographer; attributes a Cart to that photographer as `referral` when a client checks out through it. *(enforces A-6)*
- **Commission Ledger Entry** — created on a completed `referral` Cart. Amount and currency (KES) tracked, visible only on the owning Photographer's dashboard. *(enforces A-10, D-9, D-13)*
- **Resale Discount** — applied to a `resale` Cart at checkout: 13% default, studio-overridable per Photographer. *(enforces A-7, D-13)*
- **Studio Config** — single record: name, logo, brand assets. Read by every template/page at render time. *(enforces A-11, D-11)*
- **Approval** — a status on any Cart that originated from a Photographer (either path). Must be granted before the Order is finalized. *(enforces resolved former C-6 — applies to both paths)*
- **Rabbet motif** — the frame's structural groove, reused as a recurring visual motif in the UI (section dividers, card borders, transitions). A shared CSS/component treatment, not a data entity — no storage or API involved. *(enforces A-8)*

## 3. Data flow

**Enters:**
- Client photo upload (JPG/PNG) → resolution checked against selected size/glazing tier
- Catalog selections (moulding, mat, glazing, mount) — no default mount pre-selected
- Path context: referral-link token (if present), photographer-authenticated session (if resale), or neither (`direct`)
- Cart contents (1+ Orders)

**Stored:**
- Catalog Items (source of truth for pricing/tiers)
- Configurations and Orders, each with a KES price snapshot at time of add-to-cart
- Cart with its single `path` value
- Photographer accounts, Referral Links, Commission Ledger, Resale Discount rate (per-photographer override or default 13%)
- Studio Config (single row/record)
- Approval status per Cart

**Returned:**
- Live-composited preview image (client's photo + selections)
- Live running KES total as selections change
- Low-res warning payload when applicable
- Dashboard data (Photographer's own commission/discount totals only — never other photographers', never client account data, since no client accounts exist)

**Written (side effects):**
- On `referral` checkout: Commission Ledger Entry
- On `resale` checkout: Resale Discount applied to the Cart total
- On any Photographer-originated Cart: Approval record created in pending state
- On first catalog selection in a session: a `configuration_started` event
- On successful checkout: a `configuration_completed` event, linked to the same session's `configuration_started` event *(enforces E-3 — dual success metric)*

## 5. Frontend behaviour

**Landing state:** two entry points, no forced choice — "Order for myself" (client, default) vs. "I'm a photographer" (signup/login).

**Client session flow:**
1. Upload photo → resolution checked immediately
2. Select moulding → mat → glazing → mount, in any order; no mount pre-selected (D-10)
3. Live preview and live KES total update after every selection (D-2, D-3, D-13)
4. Low-res warning modal blocks selection of a size/glazing combination the photo can't support, until acknowledged (D-4)
5. Guarantee banner shown inline before "add to cart," not only in FAQ (D-6)
6. Cart view — supports multiple items (A-12); if the client arrived via a referral link, cart path is pre-set to `referral` and cannot be changed; otherwise path is `direct` (A-13 — named path, no photographer involved)
7. Checkout → M-Pesa STK push (Daraja) → confirmation on callback

**Photographer session flow:**
1. Signup (phone/email + "is this you?" checkbox) or login
2. Dashboard — commission ledger + resale discount summary, empty on first login (A-10, D-9)
3. Two actions available: "Generate referral link" (produces a copyable/shareable URL) or "Create resale order" (reuses the same configurator, but the photographer is the billing party and the client is the ship-to address)
4. Any photographer-originated cart shows a pending-approval state until approved (enforces approval step, both paths)
5. Resale checkout applies the 13% default (or studio-overridden) discount automatically; packaging output suppresses studio branding, confirmation/invoice output does not (A-7)

**Completion state:** order confirmation showing cart contents, applied path, and the resulting reward (commission accrued or discount applied) — never both.

## 7. Environment variables

- `DATABASE_URL` — Postgres connection string
- `BLOB_STORAGE_TOKEN` — photo upload storage
- `NEXT_PUBLIC_SITE_URL` — for generating referral links
- `SESSION_SECRET` — photographer session tokens
- `OTP_PROVIDER_*` — SMS/email OTP credentials (assumption — see §4 login row)
- `DARAJA_CONSUMER_KEY` / `DARAJA_CONSUMER_SECRET` — M-Pesa Daraja API credentials
- `DARAJA_SHORTCODE` / `DARAJA_PASSKEY` — STK push configuration
- `DARAJA_CALLBACK_URL` — must be a public HTTPS endpoint (Vercel deployment URL) for payment confirmation

## 9. Success criteria — what "working" looks like after first session
- A client can complete a `direct` order (stubbed path, no referral/resale) end to end, with live preview and live KES pricing
- A photographer can sign up, generate a referral link, and a client completing an order through that link produces a correct Commission Ledger Entry
- A photographer can place a resale order for a client; the 13% (or overridden) discount applies correctly, and packaging output withholds studio branding while confirmation/invoice output does not
- A cart with 2+ items from one path checks out as one transaction with the correct single reward mechanism
- Changing Studio Config name/logo updates every rendered page with zero code changes
- No mount type appears pre-selected in the UI
- The rabbet-groove motif appears consistently as a UI element (dividers/borders) across at least the configurator and cart screens
- `configuration_started` and `configuration_completed` events are recorded and `/api/metrics/conversion` returns a real start-to-complete rate
